# N3 hosted RSS failure and source-identical diagnostic

The N3 run 43049274308 reached `common-pressure-stress-diagonal-norms-ready` at 4,065,715 nodes, 166,384 ms and checkpoint RSS 5,889,191,936 bytes. It then stopped at 264,534 ms with `SOURCE_RSS_LIMIT`, observed RSS 6,783,221,760 bytes, exceeding the configured 6,442,450,944 bytes by 340,770,816. No common-family seal, N3 band, current or pressure was returned. The saved checkpoint does not identify the exact internal operation that crossed the threshold.

In the exact f8 source, the just-completed stage follows the pressure/stress seminorm construction and original `clearDisposableThirdJetCaches(G)`. The immediately next call is `attachActualCommonAdmissibleFamily({backgroundNorms,velocitySeminorms,pressureStressSeminorms},request,context)`. Its entry validates three original private norm seals, each of which may serialize large graph/program bodies. The attachment then stores an original prefix, constructs a separate source direction program, computes the selector, packs/serializes its program and stores the private seal. The recorded run cannot distinguish which of these operations consumed the extra memory. No changed source theorem or selector is inferred.

A conservative diagnostic can leave every source file, request, cutoff, private check and node bound unchanged and only change the harness: with the existing `--expose-gc`, record RSS/heap immediately before and after a forced `global.gc()` on the `common-pressure-stress-diagonal-norms-ready` checkpoint, before entering the next original constructor. A `checkCancelled` implementation may also trigger GC when RSS approaches/exceeds the configured limit, remeasure, and still throw `SOURCE_RSS_LIMIT` if it remains above the limit; rate-limit repeated GC and preserve the timeout. Checkpoints should record elapsed time, RSS, heap and peak before and after collection. JS garbage collection is not guaranteed to return RSS to the operating system or make any otherwise impossible request fit, and actual live objects/private seals must remain strongly reachable. Avoid manually clearing objects, weakening checks, truncating graph/cutoff rows, substituting serialized seals, or declaring success from a partially executed stage.

Do not increase the RSS cap solely from `/proc/meminfo`: inspect the job's `MemAvailable`, cgroup v2 `memory.max`, `memory.current`, `memory.events` or equivalent v1 counters, and reserve OS/action/other-process headroom. The observed failing RSS plus 1 GiB is 7,856,963,584 bytes; that is an example conservative reserve, not a claim that the next run needs no more. The V8 `--max-old-space-size=6100` is 6,396,313,600 bytes of old-generation limit, not a total process RSS limit. A larger host or a source-equivalence-preserving compact representation may be required. The separate N4 5-million-node-cap failure is independent of this N3 RSS failure.
